# AEB Endpoint Authentication Design

## Status: Draft

## Problem Statement

All Agent Event Bridge (AEB) proxy endpoints in `LocalMcpEndpoints.cs` use `.AllowAnonymous()`. Anyone who can reach the AEB HTTP surface can:

1. **Register fake desktops** (`POST /api/channels/register`) — inject rogue WNS channel URIs.
2. **Enumerate users** (`GET /api/channels/by-user/{upn}`) — discover which users have desktops registered.
3. **Trigger WNS notifications** (`POST /api/notify/{clientName}`) — push to any registered desktop.
4. **Inject MCP responses** (`POST /api/discovery/{requestId}/servers`, `POST /api/intune-response/{requestId}`) — poison discovery/intune results.
5. **Connect WebSockets** (`/ws/mcp/{sessionId}`) — hijack MCP sessions by guessing/learning session IDs.
6. **Read session state** (`GET /api/status/{sessionId}`, `GET /api/discovery/{requestId}/servers`, `GET /api/intune-status/{requestId}`) — no authorization on any polling endpoint.

This was acceptable during prototyping but is P1 for production.

---

## Caller Taxonomy

AEB endpoints have exactly **two caller types**:

| Caller | Transport | Examples |
|--------|-----------|---------|
| **Internal (SDK)** | Same ASP.NET process, localhost HTTP | `/api/channels/by-user/`, `/api/notify/`, `/api/mcp/`, `/api/status/`, `/api/discovery/.../servers` (GET poll), `/api/intune-check/`, `/api/intune-status/`, `/api/heartbeat/`, `/api/channels` |
| **External (locaproto)** | Internet HTTPS via WNS callback URLs | `/api/channels/register`, `/api/discovery/{requestId}/servers` (POST callback), `/api/intune-response/{requestId}` (POST callback), `/ws/mcp/{sessionId}` (WebSocket) |

The key insight: **internal callers are in-process** and share a secret trivially, while **external callers (locaproto) only learn about AEB endpoints through WNS notification payloads** — we control what's in those payloads.

---

## Design Overview

Two complementary mechanisms:

```
┌──────────────────────────────────────────────────────┐
│                AEB Proxy (ASP.NET)                    │
│                                                       │
│  ┌─────────────────┐    ┌──────────────────────────┐ │
│  │ Internal API Key │    │ Callback Token Validator │ │
│  │   Middleware     │    │     Middleware            │ │
│  └────────┬────────┘    └────────────┬─────────────┘ │
│           │                          │                │
│  SDK endpoints              locaproto endpoints       │
│  (by-user, notify,         (register, discovery       │
│   mcp, status, etc.)        callback, intune          │
│                              callback, WebSocket)     │
└──────────────────────────────────────────────────────┘
```

### Mechanism 1: Internal API Key (SDK → AEB)

A cryptographically random key generated at startup, shared in-process between the SDK services and the AEB middleware.

### Mechanism 2: Per-Request Callback Tokens (locaproto → AEB)

Short-lived, HMAC-signed, single-use tokens generated by AEB when it creates sessions/discovery requests, embedded in WNS notification payloads, and required on all callbacks from locaproto.

## Detailed Design

### 1. Internal API Key

#### Generation

At application startup, `AddLocalMcpProxy()` generates a 256-bit cryptographically random key:

```csharp
// In LocalMcpServiceCollectionExtensions.cs
public static IServiceCollection AddLocalMcpProxy(this IServiceCollection services, IConfiguration configuration)
{
    // ... existing registrations ...

    // Generate internal API key for AEB endpoint auth
    var apiKey = Convert.ToBase64String(RandomNumberGenerator.GetBytes(32));
    services.AddSingleton(new LocalMcpApiKey(apiKey));

    return services;
}
```

New model:
```csharp
// LocalMcpApiKey.cs
public sealed class LocalMcpApiKey
{
    public string Key { get; }
    public LocalMcpApiKey(string key) => Key = key;
}
```

#### Validation

A route group filter applied to all internal endpoints:

```csharp
// In MapLocalMcpEndpoints()
var internalGroup = app.MapGroup("/api")
    .AddEndpointFilter<InternalApiKeyFilter>();

internalGroup.MapGet("/channels/by-user/{userIdentifier}", ...);
internalGroup.MapPost("/notify/{clientName}", ...);
internalGroup.MapPost("/mcp/{sessionId}", ...);
internalGroup.MapGet("/status/{sessionId}", ...);
internalGroup.MapGet("/discovery/{requestId}/servers", ...); // GET poll
internalGroup.MapPost("/intune-check/{clientName}", ...);
internalGroup.MapGet("/intune-status/{requestId}", ...);
internalGroup.MapPost("/heartbeat/{sessionId}", ...);
internalGroup.MapGet("/channels", ...);
```

Filter implementation:
```csharp
public class InternalApiKeyFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var apiKey = context.HttpContext.RequestServices
            .GetRequiredService<LocalMcpApiKey>();

        var header = context.HttpContext.Request.Headers["X-LocalMcp-ApiKey"].FirstOrDefault();

        if (string.IsNullOrEmpty(header) || !CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(header),
            Encoding.UTF8.GetBytes(apiKey.Key)))
        {
            return Results.Unauthorized();
        }

        return await next(context);
    }
}
```

#### SDK-Side: Sending the Key

The SDK's `McpToolServerConfigurationService` and `WnsClientTransport` use `HttpClient` to call AEB. They must include the key.

Option A — **DelegatingHandler** (preferred):
```csharp
public class LocalMcpApiKeyHandler : DelegatingHandler
{
    private readonly LocalMcpApiKey _apiKey;

    public LocalMcpApiKeyHandler(LocalMcpApiKey apiKey)
    {
        _apiKey = apiKey;
    }

    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        request.Headers.TryAddWithoutValidation("X-LocalMcp-ApiKey", _apiKey.Key);
        return base.SendAsync(request, cancellationToken);
    }
}
```

Register in DI:
```csharp
services.AddHttpClient("LocalMcpProxy")
    .AddHttpMessageHandler<LocalMcpApiKeyHandler>();
```

Option B — Direct injection into `WnsClientTransport` constructor (if named HTTP client is too heavy).

**Trade-off**: Option A is cleaner (transparent to transport code), Option B is simpler for one-off use.

**Recommendation**: Option A.

### 2. Callback Tokens (locaproto → AEB)

Callback tokens authenticate locaproto when it calls back to AEB after receiving a WNS notification.

#### Token Model

```
CallbackToken = Base64Url( HMAC-SHA256(secret, payload) ) + "." + Base64Url(payload)

payload = {
    "sub": "<requestId or sessionId>",
    "iat": <unix timestamp>,
    "exp": <unix timestamp>,  // short TTL (5 min for discovery, 2 min for MCP sessions)
    "scope": "discovery" | "intune" | "mcp-session" | "registration"
}
```

These are intentionally NOT JWTs — they are lightweight, self-contained, HMAC-signed tokens. The signing secret is the same API key generated at startup (or a derived key if separation is desired).

#### Token Generation (AEB side)

New service:
```csharp
public interface ICallbackTokenService
{
    /// <summary>
    /// Generates an HMAC-signed callback token for the given subject and scope.
    /// </summary>
    string GenerateToken(string subject, string scope, TimeSpan ttl);

    /// <summary>
    /// Validates a callback token and returns the subject if valid.
    /// Returns null if invalid, expired, or tampered.
    /// </summary>
    string? ValidateToken(string token, string expectedScope);
}
```

Implementation:
```csharp
public class CallbackTokenService : ICallbackTokenService
{
    private readonly byte[] _signingKey;

    public CallbackTokenService(LocalMcpApiKey apiKey)
    {
        // Derive a separate key for callback tokens using HKDF
        _signingKey = HKDF.DeriveKey(
            HashAlgorithmName.SHA256,
            Encoding.UTF8.GetBytes(apiKey.Key),
            32,
            info: Encoding.UTF8.GetBytes("aeb-callback-token"));
    }

    public string GenerateToken(string subject, string scope, TimeSpan ttl)
    {
        var payload = JsonSerializer.SerializeToUtf8Bytes(new
        {
            sub = subject,
            iat = DateTimeOffset.UtcNow.ToUnixTimeSeconds(),
            exp = DateTimeOffset.UtcNow.Add(ttl).ToUnixTimeSeconds(),
            scope = scope
        });

        var payloadB64 = Convert.ToBase64String(payload);
        var signature = HMACSHA256.HashData(_signingKey, payload);
        var signatureB64 = Convert.ToBase64String(signature);

        return $"{signatureB64}.{payloadB64}";
    }

    public string? ValidateToken(string token, string expectedScope)
    {
        var parts = token.Split('.', 2);
        if (parts.Length != 2) return null;

        var signatureB64 = parts[0];
        var payloadB64 = parts[1];

        var payload = Convert.FromBase64String(payloadB64);
        var expectedSig = HMACSHA256.HashData(_signingKey, payload);

        if (!CryptographicOperations.FixedTimeEquals(
            Convert.FromBase64String(signatureB64), expectedSig))
            return null;

        var doc = JsonDocument.Parse(payload);
        var exp = doc.RootElement.GetProperty("exp").GetInt64();
        if (DateTimeOffset.UtcNow.ToUnixTimeSeconds() > exp)
            return null;

        var scope = doc.RootElement.GetProperty("scope").GetString();
        if (scope != expectedScope)
            return null;

        return doc.RootElement.GetProperty("sub").GetString();
    }
}
```

#### Token Injection into WNS Payloads

Each `Send*NotificationAsync` method already constructs a JSON payload. We add a `callbackToken` field:

**SendNotificationAsync** (MCP session invocation):
```diff
 var notification = new
 {
     callback = callbackUrl,
     serverId = serverId,
     serverType = "local",
     agentAppId = agentAppId,
+    callbackToken = tokenService.GenerateToken(sessionId, "mcp-session", TimeSpan.FromMinutes(5)),
     timestamp = DateTime.UtcNow
 };
```

**SendCloudMcpNotificationAsync** (cloud MCP):
```diff
 var notification = new
 {
     callback = callbackUrl,
     serverId = cloudConfig.ServerId,
     serverType = "cloud",
     agentAppId = agentAppId,
     cloudConfig = new { ... },
+    callbackToken = tokenService.GenerateToken(sessionId, "mcp-session", TimeSpan.FromMinutes(5)),
     timestamp = DateTime.UtcNow
 };
```

> **Note**: The sessionId must be extracted from the callback URL and passed to the notification service. Currently the `/api/notify/{clientName}` endpoint creates the sessionId and builds the callback URL — it will also generate the token and embed it.

**SendDiscoveryNotificationAsync** (server list):
```diff
 var notification = new
 {
     type = "list_servers",
     requestId = requestId,
     callbackUrl = callbackUrl,
+    callbackToken = tokenService.GenerateToken(requestId, "discovery", TimeSpan.FromMinutes(5)),
     timestamp = DateTime.UtcNow
 };
```

**SendIntuneCheckNotificationAsync** (Intune status):
```diff
 var notification = new
 {
     type = "intune_status",
     requestId = requestId,
     callback = callbackUrl,
+    callbackToken = tokenService.GenerateToken(requestId, "intune", TimeSpan.FromMinutes(5)),
     timestamp = DateTime.UtcNow
 };
```

#### Token Validation on External Endpoints

External callback endpoints validate the `X-Callback-Token` header:

```csharp
var externalGroup = app.MapGroup("/api")
    .AddEndpointFilter<CallbackTokenFilter>();

externalGroup.MapPost("/discovery/{requestId}/servers", ...);   // POST callback
externalGroup.MapPost("/intune-response/{requestId}", ...);      // POST callback
```

Filter:
```csharp
public class CallbackTokenFilter : IEndpointFilter
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext context,
        EndpointFilterDelegate next)
    {
        var tokenService = context.HttpContext.RequestServices
            .GetRequiredService<ICallbackTokenService>();

        var token = context.HttpContext.Request.Headers["X-Callback-Token"].FirstOrDefault();
        if (string.IsNullOrEmpty(token))
        {
            return Results.Json(new { error = "Missing callback token" }, statusCode: 401);
        }

        // Determine expected scope from the route
        var path = context.HttpContext.Request.Path.Value ?? "";
        string expectedScope;
        if (path.Contains("/discovery/"))
            expectedScope = "discovery";
        else if (path.Contains("/intune-response/"))
            expectedScope = "intune";
        else
            expectedScope = "mcp-session";

        var subject = tokenService.ValidateToken(token, expectedScope);
        if (subject == null)
        {
            return Results.Json(new { error = "Invalid or expired callback token" }, statusCode: 401);
        }

        // Optionally: verify subject matches the route parameter
        // e.g., for /api/discovery/{requestId}/servers, verify subject == requestId

        return await next(context);
    }
}
```

#### WebSocket Authentication

The `/ws/mcp/{sessionId}` endpoint requires special handling since WebSocket upgrade requests can't easily include custom headers from all clients.

**Approach**: Token as query parameter.

The callback URL sent in WNS already contains the sessionId:
```
wss://agent.com/ws/mcp/{sessionId}?serverId=xxx
```

We add the token:
```
wss://agent.com/ws/mcp/{sessionId}?serverId=xxx&token={callbackToken}
```

Validation in the WebSocket endpoint:
```csharp
app.Map("/ws/mcp/{sessionId}", async (HttpContext context, string sessionId, ISessionManager sessionManager) =>
{
    // Validate callback token from query string
    var tokenService = context.RequestServices.GetRequiredService<ICallbackTokenService>();
    var token = context.Request.Query["token"].FirstOrDefault();

    if (string.IsNullOrEmpty(token))
    {
        context.Response.StatusCode = 401;
        return;
    }

    var subject = tokenService.ValidateToken(token, "mcp-session");
    if (subject == null || subject != sessionId)
    {
        context.Response.StatusCode = 401;
        return;
    }

    // ... existing WebSocket handling ...
});
```

#### Registration Endpoint Auth

`POST /api/channels/register` is unique — it's the first call locaproto makes to AEB, before any WNS notification has been sent. The flow is:

1. User clicks a `locaproto:?action=register&callback=https://agent.com/api/channels/register&user=upn` link
2. locaproto launches, extracts the callback URL
3. locaproto POSTs registration data to the callback

**Option A — Registration token in the protocol URL** (recommended):

When the SDK generates the `locaproto:` URL (in the `/api/channels/by-user/` 404 response and in `/api/notify/` 404 response), it embeds a registration token:

```
locaproto:?action=register
  &callback=https://agent.com/api/channels/register
  &user=upn@contoso.com
  &regToken={callbackToken with scope "registration", TTL 10 minutes}
  &serverIds=...
```

locaproto extracts `regToken` and includes it in the `X-Callback-Token` header when POSTing to `/api/channels/register`.

The registration endpoint validates the token with scope `"registration"` and verifies the `sub` claim matches the user identifier.

**Option B — Separate registration challenge-response**: AEB exposes a `/api/register/challenge` that returns a nonce; locaproto signs it. More complex, deferred to future.

**Recommendation**: Option A for initial implementation.

## Configuration

### appsettings.json additions

```json
{
  "LocalMcpProxy": {
    "IdleTimeoutSeconds": 120,
    "McpRequestTimeoutSeconds": 120,
    "DefaultServerId": "...",
    "BaseUrl": "...",
    "EnableEndpointAuth": true,
    "CallbackTokenTtlMinutes": 5,
    "RegistrationTokenTtlMinutes": 10
  }
}
```

- **`EnableEndpointAuth`** — Master switch. When `false`, all endpoints remain anonymous (for dev/test). Default: `true`.
- **`CallbackTokenTtlMinutes`** — TTL for MCP session, discovery, and intune callback tokens. Default: 5.
- **`RegistrationTokenTtlMinutes`** — TTL for registration tokens embedded in `locaproto:` URLs. Default: 10.

## Security Analysis

### What This Fixes

| Threat | Before | After |
|--------|--------|-------|
| Rogue desktop registration | Anyone can POST to `/api/channels/register` | Requires valid registration token from `locaproto:` URL |
| User enumeration via `/api/channels/by-user/` | Open | Requires internal API key (inaccessible from outside) |
| Fake WNS notifications via `/api/notify/` | Open | Requires internal API key |
| Discovery result poisoning | Anyone can POST to `/api/discovery/{id}/servers` | Requires callback token matching the requestId |
| MCP session hijacking | Guess the sessionId GUID | Requires HMAC-signed callback token |
| Intune result injection | Open | Requires callback token |
| Session status leaking | Open | Requires internal API key |

### Residual Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Registration token in `locaproto:` URL visible in browser history | Low | Short TTL (10 min); single-use (revoke after successful registration) |
| WebSocket token in URL visible in server logs | Low | Tokens are short-lived; can add log scrubbing |
| Internal API key compromise if app memory is dumped | Low | Same risk as any in-process secret; no worse than existing WNS credentials |
| HMAC signing key rotates on app restart | Medium | All existing sessions/tokens are invalidated. Acceptable for single-instance; for scaling, use shared key store |
| Callback token replay within TTL window | Low | Tokens are scoped to specific requestId/sessionId; replay targets same resource |

### Out of Scope (Future Work)

1. **Mutual TLS between locaproto and AEB** — Would provide transport-level auth.
2. **Per-session single-use tokens** — Token revocation after first use (prevents replay entirely).
3. **Registration challenge-response** — More robust than embedding token in URL.
4. **Distributed key storage** — Required for horizontal scaling of AEB.

## Implementation Order

### Phase 1: Internal API Key (SDK → AEB) — Low Risk
1. Create `LocalMcpApiKey` model
2. Generate key in `AddLocalMcpProxy()`
3. Create `InternalApiKeyFilter`
4. Create `LocalMcpApiKeyHandler` (DelegatingHandler)
5. Refactor endpoints into route groups with filter
6. Wire up named HttpClient in SDK services
7. Add `EnableEndpointAuth` toggle

**Validates**: All SDK-to-AEB calls still work with API key injection.

### Phase 2: Callback Tokens (locaproto → AEB) — Medium Risk
1. Create `ICallbackTokenService` / `CallbackTokenService`
2. Embed `callbackToken` in WNS notification payloads
3. Create `CallbackTokenFilter`
4. Add token validation to WebSocket endpoint
5. Add token to `locaproto:` registration URLs

**Requires**: Coordinated update of locaproto to extract and forward tokens.

### Phase 3: locaproto Changes — Coordinated Deploy
1. Update `McpNotification` model to include `CallbackToken`
2. Update `WnsNotificationHandler` to extract token from payload
3. Update `McpClientProxy` to append token to WebSocket URL
4. Update `AgentRegistrationManager` to extract `regToken` from `locaproto:` URL

**Deploy order**: AEB (Phase 1+2) first with `EnableEndpointAuth = false`, then locaproto (Phase 3), then enable auth (`EnableEndpointAuth = true`).

## Rollback Plan

Set `"EnableEndpointAuth": false` in `appsettings.json` to immediately disable all auth checks and revert to anonymous behavior. No code changes needed.
